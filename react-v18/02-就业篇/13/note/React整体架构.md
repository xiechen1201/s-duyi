# React整体架构

Reacr v15 之前的架构称为 Stack 架构，v16 之后重构了整体的架构，新的架构称为 Fiber 架构，新的架构相比旧的结构最大的特点就是实现时间切片。

## 旧架构的问题？

哪些情况会导致我们的 Web 应用无法快速响应？

总结就是两个大类：

1、执行大量的计算或者设备本身不足，页面就会掉帧卡顿，本质上是来自 CPU 的瓶颈；

2、进行 i/o 操作，需要等待数据返回后再进行后续的操作，等待的过程中无法快速响应，来自于 i/o 的瓶颈；

### cpu 瓶颈

网页是一帧帧绘制出来的，就像一个画家画画一样。网页中动画效果（轮播图、百叶窗），本质上就是浏览器不停的进行绘制。

大多数的设备基本都是 60fps，这意味着 1s 就要绘制 60 次， 1000ms / 60 = 16ms，也就是说浏览器每隔 16.66ms 就需要绘制一帧。

浏览器绘制画面之前实际上还有很多的事情要做：（图片渲染流水线），每次执行流水线的时候，大致需要上面的一些步骤，而不是全部的步骤。

按照性能高低进行排序：合成 > 重绘 > 重排

前面说了，浏览器绘制是 16.66ms，但是执行 JS 和渲染流水线是在同一个线程上面执行，也就意味着如果 JS 执行的时间过长，就会导致绘制时间过长，从而导致掉帧卡顿。

（小球动画案例）

React16 之前就存在 JS 代码执行时间过长，导致绘制时间过长，导致掉帧卡顿的问题。在 React 中需要去计算（diff 比较）整棵虚拟 DOM 树，虽然说是 JS 层面的计算，相比 DOM 节省了很多时间，但是每次重新计算整棵虚拟 DOM 树，会导致每一帧的 JS 执行时间过长，从而导致动画和一些实时更新得不到及时的响应，造成卡顿的视觉现象。

在 React16 版本之前，再进行两棵虚拟 DOM 数进行对比的时候，需要遍历上面的结构，这个时候只能使用递归，而且这种递归是不可能够打断的，从而导致了 JS 时间过长。

这样的架构模式就称为 Stack 架构模式，因为采用的是递归，会不停的开启新的函数栈。

### i/o 瓶颈

对于前端来说，主要就是网络延迟。

网络延迟是客观存在的现象，如何减少这种现象对用户的影响呢？React 团队给出的答案是将人机交互的研究成果整合到 UI 中。

用户对卡顿的感知是不同的，输入框哪怕有轻微的延迟，用户也会认为很卡。假如是加载一个 list，哪怕 loading 好几秒，用户也不会觉得卡顿，这就是人机交互的研究成果。

对于 React 来讲，所有的操作都来自于自变量的变化，导致重新渲染，我们只需要针对不同的操作赋予不同的优先级即可。

以下三点：

1、不同的优先级

2、统一调度，优先处理高优先级的任务

3、更新正在进行，更高优先级的任务会中断当前的任务，优先处理高优

要实现上面的 3 点，就需要 React 底层能够实现：

- 可以调度优先级的调用器；

- 调用对应的调用算法

- 支持可中断的虚拟 DOM

不管是解决 CPU 的瓶颈还是 IO 的瓶颈，底层的诉求都需要实现 time slice。

## 新架构的思路

### 解决 CPU 瓶颈

从 React16 开始就引入了 Fiber 的概念，这是一种通过链表来描述 UI 的方式，本质上也可以看作是虚拟 DOM 的实现。

Fiber 本质上也是一个对象，但是和 React 元素不同的地方在于对象之间使用链表的结构进行串联。

```
child: null,    // 第一个孩子
sibling: null,  // 下一个兄弟
return: null    // 父节点
```

> 链表 = 一个节点保存数据，同时保存“下一个节点”的引用。

（图片示例）

使用链表这种结构最大的好吃就是在进行整棵树对比计算（reconcile）的时候这个过程是可以被打断的。在发现一帧是不够的情况下，不能够继续执行 JS ，需要渲染下一帧的时候，这个时候就会打断 JS 的执行，优先渲染下一帧。渲染完成后，再接着回来完成上一次没有执行完的 JS 计算。

### 解决 i/o 瓶颈

从 React16 开始引入了 Scheduler 调度器，用来调度任务的优先级。

在 react16 之前：

- Reconciler 协调器：vdom 的实现，根据自变量的变化计算出 UI 的变化；

- Renderer 渲染器：将 UI 的变化渲染到宿主环境；

从 React16 开始多了一个架构组件，就是 Scheduler 调度器。

- Scheduler 调度器：用来调度任务的优先级，高优先级的任务会优先进入到 Reconciler 中；

新架构中 Reconciler 的更新流程也从之前的递归变成了可中断的循环过程。不能够继续执行 JS 的是就中断 UI 的计算；
